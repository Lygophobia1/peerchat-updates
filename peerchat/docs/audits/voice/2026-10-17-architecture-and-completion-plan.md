# Android voice architecture and completion plan

Audit date: 2026-10-17. Source checkpoint: `be502d290df55cf45ca271923ceae3b60e6ea103`, branch `codex/native-unicode-emoji`. The target worktree was clean when inspected. The full user request was read from the supplied attachment. Accepted dev.180 device names and authorization remain outside the implementation changes below. The production checkpoint reported by orchestration is `2cb3f0e`; this audit makes no deployment claim.

## Decision and acceptance status

Reuse the existing shared native engine and pinned WebRTC NetEq receive adapter. Do not replace NetEq, turn a capability flag on without its real library, or introduce a separate Android/group engine. The smallest supported dependency path is a Linux build of the existing WebRTC `pc_rx` adapter with all required static dependencies, followed by an Android ARM64 link and an exercised real receive pipeline.

The Android foundation is substantial but is not a working Android call product. Its real transport and Opus code are compiled, while the actual Android NetEq dependency is absent. Call controls, lifecycle ownership, and group application orchestration are also incomplete. Physical Motorola direct calling and physical multiparty acceptance remain outstanding. No physical device install, Pi deployment, remote push, or server authorization change is part of this audit.

Two Android controller security/lifecycle defects were independently reproduced and corrected during this audit. Those focused fixes do not enable Android calling and are not receive-pipeline validation.

## Existing ownership and data flow

### Direct calling

`portable/peerchat_core.cpp` owns the profile's `CallManager`, `AndroidVoiceApplication`, verified contacts, authenticated friend snapshot, active session transports, and reliable endpoints. `VoiceBridge.request` is an opaque, bounded JNI operation record; it checks the profile handle, account and current authentication generation before mutating the call. JNI currently exposes snapshot, start, answer, decline, end, mute, deafen, and authenticated TURN configuration.

`portable/android_voice_application.hpp` connects this profile state to `portable/voice_application.hpp`. Its authorization gate requires the current friend account/device association, a locally verified contact, and the public key hashing to the expected peer ID. Signaling uses only the ready winning `ReliableEndpoint` for that peer. `portable/reliable_endpoint.hpp` rechecks authorization, authenticated session readiness, and negotiated voice/recovery capabilities. Archive and group-key-only sessions cannot become direct-call signaling endpoints.

`VoiceApplication` owns application progression and uses the existing `CallManager` for call identity, lifetime, media generation, ring/connect deadlines, deterministic glare handling, bounded candidate queues and recovery. Incoming `CallOffer` rings without creating media. Explicit Answer creates the receiver. A remote `CallConnected` cannot assert that local media connected. Receive bindings carry peer identity, call ID, call lifetime and media generation; RTP/SSRC never supplies account identity.

`voice_media.cpp` owns libdatachannel peer connections/tracks, ICE, DTLS-SRTP, Opus sending, the existing platform `Audio` adapter, and `VoiceReceiveEngine`. Capture is mono signed PCM at 16 kHz, 320 samples/20 ms. Opus is configured for VOIP, approximately 24 kbit/s, complexity 5 and in-band FEC. RTP uses payload type 111 and the required 48 kHz clock (960 ticks per 20 ms). The bidirectional local sendrecv track receives packets too; this is essential when negotiation does not create a separate remote track.

Authenticated media track callbacks insert RTP into `VoiceReceiveEngine`; that validates the bound source/generation, RTP framing, payload type and stable SSRC. It delegates to the existing C `pc_rx` ABI in `audio_receive/peerchat_audio_receive.cpp`. Each authorized source owns a real WebRTC NetEq and Opus decoder. The WebRTC mixer produces mono 16 kHz output in 10 ms blocks. The output device pulls two blocks for each 20 ms frame. There is no additional receive PCM queue between NetEq and the output worker. Deafening continues to advance NetEq while suppressing samples, preventing old audio replay on undeafen.

Receive callbacks acquire a shared receive context by library track ID, and retired generations are removed before codec/device teardown. The source key is authorization context, not a transport address or SSRC. NetEq and source/mixer registries are bounded. Busy receive locks return bounded silence/drop results rather than blocking the device on retries.

### Android audio and processing

`portable/audio_android.cpp` implements the same `Audio` abstraction through JNI callbacks to `AndroidAudioDevice`. Tokens are monotonically allocated; the registry yields shared state for callback lifetime safety. Capture and playout use 320-sample short arrays. The current path makes a JNI array copy and a 640-byte native PCM allocation/conversion per capture frame; it does not create a new encoder per frame or per recipient. Those copies are bounded and should be measured before changing the interface.

Audio state uses separate state/callback locks. Stop marks inactive, drains callbacks, removes the token, and invokes Java device cleanup. Muting clears capture buffers and stops the Android recorder. Device failures set a bounded native error rather than recording PCM in diagnostics. The Kotlin adapter uses AudioRecord/AudioTrack, worker threads, bounded output buffering, audio focus and Android session effects.

Android `portable/voice_apm_android.hpp` honestly reports WebRTC APM unavailable and preserves PCM. Optional Android AudioRecord effects are a separate backend; their presence is device dependent. Do not report native WebRTC APM, echo cancellation or its Windows presets as active on Android merely because capture succeeds. Speakerphone/AEC suitability needs physical testing.

The root Android audit found no caller for `AndroidCallAudio.prepare`, no working application start/answer command path, and diagnostic-only presenter controls. The manifest has RECORD_AUDIO and audio settings permissions, but the only existing foreground service is for data sync. Current app runtime UI/transfer leases and a 60-second background grace are not call ownership.

### TURN and encryption

`media_ice_configuration.hpp` is deliberately production relay-only. `DirectTestOnly` is guarded by a test macro. Production media uses TURN UDP, short-lived credentials and authenticated profile/discovery/configuration generations; this is not a direct-first ICE policy with TURN fallback. Changing that policy is outside the smallest completion path.

`AndroidVoiceApplication::installIce` rejects stale generations, expired credentials and unauthenticated scopes. Old credentials are cleared when replaced or invalidated. A call factory requires current valid credentials and current peer authorization. Recovery recreates a fresh media endpoint, bounded by the existing recovery window; there is no safe basis for reusing a superseded authenticated session.

The server relays signaling and encrypted DTLS-SRTP packets. The Pi does not receive decoded voice samples in this design. Direct-call SDP/DTLS fingerprint exchange remains on verified peer signaling. Group signaling uses the existing authenticated server room protocol and its current trust boundary; this audit does not substitute a new end-to-end group signaling protocol.

## Android NetEq dependency blocker

`android/voice-media/CMakeLists.txt` already compiles shared `voice_media.cpp`, `voice_receive_engine.cpp`, `group_voice_session.cpp`, and `voice_media_topology.cpp` for ARM64. It pins Opus, libdatachannel, MbedTLS and the transport's dependencies. `PEERCHAT_ANDROID_RECEIVE_LIBRARY` is an explicit path to a static `pc_rx` archive. Supplying it sets `PEERCHAT_ANDROID_STATIC_RECEIVE`; otherwise `androidVoiceAvailable()` is false and the native engine rejects call creation.

The absent component is the real Android build of `audio_receive/peerchat_audio_receive.cpp` and its pinned WebRTC NetEq/audio decoder/mixer dependency closure. It is not a missing implementation of the jitter buffer. Windows has this adapter and focused production-engine tests. Android's existing instrumented `NativeVoiceApplicationTest` explicitly verifies that unavailable media cannot create calls; its passing result cannot be called audio proof.

The independent dependency audit found pinned WebRTC `6cf6bcb`, an Android GN toolchain requiring Linux, `checkout_android=False`, no Android NDK bundle in that checkout, and no runnable local WSL distribution/container. The smallest supported proposal is the existing GN adapter target with `complete_static_lib=true` on Linux, CPU arm64, Android minimum SDK 26 matching the app (the pinned WebRTC default is 29). Record exact commit, arguments, build tools, target dependency closure and output hashes. Verify ELF machine/API requirements, unresolved symbols, C++ ABI/runtime compatibility, duplicate Opus dependencies, licensing and 16 KiB page compatibility in the final shared library/APK. Do not silently patch out the Linux-host requirement or label a Linux-host archive as Android.

Keep the capability unavailable until the actual Android artifact is linked and exercised. A source-only lifecycle improvement or a build with no NetEq archive remains a foundation build.

## Group foundation and authorization

`GroupVoiceSession` already separates room authorization supplied by the application from media work. It owns one `LocalVoiceSource` encoder/DSP, one receive/mixer owner, one audio device, and a topology. `RelayMeshVoiceTopology` creates per-peer libdatachannel DTLS-SRTP connections. The one encoded Opus packet is fanned out; each remote source has its own NetEq/decoder. The default device implementation has a Windows-oriented class name but uses the shared `Audio` abstraction, which already resolves to Android's implementation when compiled there.

`desktop/GroupVoiceService.cs` supplies the application reference: explicit join/leave, authenticated room snapshots, current epoch and local participation token, roster reconciliation, TURN configuration, bounded signaling queues and teardown when the authenticated event channel/participation disappears. `group_voice_bridge.cpp` is a Windows wchar/DLL boundary; Android should invoke `GroupVoiceSession` from an opaque JNI application adapter rather than compiling that Windows ABI or creating another media engine.

`server/GroupMediaRooms.cs` already implements room snapshots, joins/leaves and signaling. It authorizes every operation against the current roster and current authenticated event session; mutations bind epoch/revision/roster generation. It issues a distinct public media participation token per device/session lifetime. Signaling validates the current source session and participation, current target membership/participation, target live session, route ID and media generation. The server derives sender identity from the authenticated session, rejects unauthorized fields, bounds messages/rate, and serializes mutation/signaling admission. Disconnect and roster reconciliation remove participation. These boundaries must remain intact.

Android currently discards `group_room_snapshot`, `group_room_result`, `group_media_signal` and `group_media_result` in `ForegroundEvents.kt`. Its outbound `queueGroup` only admits text send/ack. Thus native group compilation is not Android group signaling integration. Completion requires a bounded current-session room projection and command/signal application owner, with server-authorized participants mapped to native source keys. Do not use historical encrypted group epochs or unrelated membership as live-room permission. Clear projection/queues/media on account/profile/authentication-session replacement, event channel loss, room epoch change, local participation replacement, removal or revocation. Reconcile removed sources before processing their queued signals.

No new server authorization boundary is necessary for the basic reuse design. If production proves not to support these existing operations, stop for the user's server/security approval; do not deploy a server change as an implicit client fix.

### Group limits and incomplete recovery

Native receive/topology permits at most 32 remote sources (33 local-plus-remote devices), while the server room allows 64 devices. The client must enforce/display a supported bound and fail cleanly when the server snapshot exceeds it; the server limit does not prove usable Android capacity. A smaller tested product limit is appropriate after measurement.

For N participants, each endpoint runs one encoder and N-1 decoders/NetEq sources and sends/receives N-1 media streams. At 24 kbit/s Opus payload alone, each endpoint uses about `24*(N-1)` kbit/s each direction, before packet, SRTP and TURN overhead. At 4 participants that is about 72 kbit/s; at 8 it is about 168 kbit/s. These are estimates, not measured traffic or battery results. The relay mesh has quadratic aggregate route/relay work. One local encode avoids quadratic local encoding, but decoding, mixing, network and encryption grow with peers.

`RelayMeshVoiceTopology::signaling` currently accepts media generation 1 only, and failed endpoints remain in its endpoint map. It has no automatic same-participation media restart implementation. Existing leave/rejoin creates a fresh participation and is the clear supported recovery primitive. Do not promise seamless group Wi-Fi/cellular recovery until it is implemented and tested using existing protocol generations or a deliberate fresh participation. The current session snapshot also lacks per-source speaking levels; a speaking indicator requires bounded source-level observation, not guessing from packet receipt.

Media uses separate RTP/DTLS-SRTP paths from reliable text/transfers. That avoids sharing the same ordered bulk-data stream, but does not guarantee OS/network QoS or absence of shared CPU/upload contention. Exercise active file transfer and History Sync alongside calls before making priority/performance claims.

### Runtime lease integration deferred with a concrete prerequisite

`AndroidMessagingRuntime.kt` was inspected for a useful independent call lease change while the Linux prerequisite was pending. It delegates to the one `MessagingBackend`, but its public `MessagingSnapshot` contains account/local peer and `VoiceSnapshot` without the backend's private authentication generation or profile/session identity. Native voice snapshots are refreshed through `MessagingBackend.tickAfterMailbox`; `clearAuthorization` invalidates native voice without immediately clearing that specific snapshot field. Offline/reset projection subsequently clears it through `localOfflineSnapshot`, but this is not a generation-fenced service ownership seam.

An observer that automatically retained the runtime whenever the projected call looked active could retain stale/superseded state. A new `acquireCall` method with no actual service owner or command caller would be dormant code rather than completed background support. Therefore no Android runtime or lease policy was changed in this checkpoint. The prerequisite is a current backend-owned call projection carrying profile/session/authentication scope and native call identity/lifetime, coupled to the explicit microphone service lifetime. Acquire only after authorized user Start/Answer; release on current call end or scope replacement; reject stale notification actions against that exact scope. Add focused tests at that real integration boundary. Preserve existing UI, transfer, archive and wake policies while doing so.

## Focused fixes completed and validation evidence

Only `portable/voice_application.hpp` and `tests/android_voice_application_test.cpp` were changed for these fixes. No wire protocol, authorization store, server, Windows node or accepted device-name implementation was altered.

**Incoming-call consent during local recovery.** An unanswered incoming offer had `mediaRecoveryCapable=true`. A local `networkChanged()` called `interrupt()`, and `serviceRecovery()` could create an outgoing media offer when the local identity sorted first. This bypassed Answer even though the separate remote-restart path correctly rejected an Incoming call. The reproduced failure was `Local network recovery bypassed incoming-call acceptance` in build evidence directory `build/tests/android-voice-application-d002b5fa8fbb45a8bd6aaa594c5a00ff`. The fix makes interruption a no-op while the state is Incoming and independently rejects Incoming at the recovery consumer. Regression tests cover both deterministic identity orderings, repeated local network changes/ticks, no factory/media, unchanged initial generation, no recovery signaling, and subsequent explicit Answer. A separate fixture deliberately seeds CallManager retry state while Incoming and confirms the consumer still cannot create media or signal recovery.

**Mute restored before recovered device startup.** The controller formerly reapplied mute only after `VoiceMedia::poll()` returned Connected, but that production poll starts Audio before returning the event. A replacement muted call could therefore briefly start unmuted. The reproduced controller failure was `Media recovery started microphone before restoring mute`, directory `build/tests/android-voice-application-3c1b110be5b94e93b099cb306522e925`. The fix applies preserved mute after `startOffer`/`startAnswer` has created Audio and before the first poll can start its device. Android `Audio::setMuted` supports this pre-start state. Tests exercise both recovery offerer/answerer, a muted explicit incoming Answer, and stop-before-device-start if preparing mute fails.

The final focused suite passed with strict warning compilation and existing tests for availability/authentication, unchanged signaling, candidate bounds, consent, glare/replay, generation fencing, mute/deafen, recovery, timeout and teardown. Evidence: `build/tests/android-voice-application-1d5161e3903a42f080edd3c3df5bcec7`. `git diff --check` passed. These are explicit fake-media controller UNIT tests; the fake now models the real poll-before-Connected device-start ordering. They do not produce audio, ICE, DTLS, RTP, Android device activity or E2E evidence. They demonstrate regression prevention in the controller and require real Android audio testing after dependency integration.

## Remaining test and performance obligations

Retain the existing production receive/transport/topology tests (`tests/voice_receive_engine_test.cpp`, `voice_media_transport_test.cpp`, `voice_receive_lifetime_test.cpp`, `group_voice_session_test.cpp`, `voice_topology_test.cpp`) and relevant Windows call/screen compatibility regressions. Re-run them as required for the final scope; this audit did not claim new execution of those suites.

Android tests must cover permission denial, focus loss, route disappearance and Bluetooth/wired changes, failed recorder/player setup, activity recreation, lock/background operation, generation-fenced notification actions, and cleanup after call/service death. Native/controller tests must cover stale/reordered signaling, superseded peer sessions, revocation, bounded recovery, teardown, repeated calls and group participant changes. Cross-platform integration must exercise the production NetEq pipeline and DTLS-SRTP transport with simultaneous speakers and bulk transfers. Physical Motorola tests must verify two-way audio in both DM directions, Android-to-Android, lock/background behavior and multi-device group calls.

Existing native measurement points include Opus encode spans, RTP arrival observations, NetEq receive pulls/delay/concealment, counters and audio device activity. No end-to-end mouth-to-ear latency, CPU, battery or Android power measurements were made in this audit. A 20 ms frame and bounded buffers are format/configuration facts, not a measured latency guarantee. Keep host component proof, Android emulator evidence and physical acceptance reported separately.
