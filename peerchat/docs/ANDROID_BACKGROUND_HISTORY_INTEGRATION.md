# Android bounded background History Sync

The dev.166 background lease deliberately admitted mailbox work only. The coordinator returned before reading native archive progress or starting archive relays, and the wake job could finish immediately after mailbox publication. This prevented previously authorized History Sync from continuing during that job even when Android granted execution time.

The existing process-local runtime now has a separate bounded archive capability. The same 30-second JobScheduler job authenticates the remembered account, refreshes signed archive authorization through the existing native enrollment adapter, and resumes the existing native History Sync engine. The archive lease does not admit new friend reconnects, group-control routes, or file-transfer routes. Foreground and explicit transfer leases retain their existing capabilities.

Leaving the foreground with pending archive work schedules the existing coalesced reconciliation job. Mailbox completion cannot finish that job before a fresh native archive projection settles. A waiting source, interrupted archive import, active provider, or unavailable status keeps work pending until the budget expires; the scheduler then owns exponential retry and network constraints. The retry job is persisted across reboot. Existing six-hour persisted reconciliation also runs for remembered accounts with mailbox storage disabled, because mailbox storage consent and signed History Sync authorization are independent. Actual mailbox operations still honor mailbox consent, and archive operations still require the original verified grants and provenance.

Native encrypted storage remains the sole owner of sync intent, per-source conversation cursors, deduplication, grants and imports. No extra cursor database, engine, account identity, historical authorization or permanent foreground service was introduced. Native metadata refresh and relay retry remain bounded; server mailbox publication is serviced before archive work on each coordinator pass.

Terminal native fail-closed, paused and disabled activities do not generate repeated background retries. They retain their native error/policy status; the scheduler does not attempt to repair rejected authorization or corrupt state by starting its own scan.

Stale archive status now displays Waiting, including when the previous snapshot was Complete. A failed incoming archive demand clears the current completion projection and retains the previous completed-result counters separately. A relay rendezvous failure is not proof of missing history, successful completion, or an Android lifecycle failure. Existing stage/class diagnostics distinguish rendezvous, TLS admission, transport I/O and server authorization errors without logging credentials or message contents.

## Validation and physical limits

Focused host tests cover archive-only lease capability and deadlines, active/waiting/stale/failed/provider completion gating, disabled and paused policy, stale completion presentation, persisted network-constrained retry scheduling, and existing protected mailbox notification publication. The final offline Gradle run passed 28 tests with zero failures/errors: ArchiveEnrollmentExecutionTest (7), ArchiveStatusTest (5), ArchiveWakePolicyTest (3), BackendLeasePolicyTest (3), OpaqueWakeSchedulingTest (9), and WakeMailboxPublicationTest (1). Existing archive enrollment/status tests remain in the selected regression set.

Host tests cannot determine the actual cause of the previously supplied dev.166 archive relay failure or prove Wi-Fi/cellular handoff, Motorola locked-screen behavior, or source availability. Physical acceptance must correlate the phone's archive attempt/stage/reason and native authorization diagnostic with the authorized source's availability. A genuinely unavailable source stays pending; it cannot be repaired by extending Android execution time.

Android Doze, quota, network restrictions, force-stop and vendor battery policy can defer these jobs. There is no promise of continuous background synchronization or a deadline for completion. A remembered login is necessary for process-recreated authenticated work. Profiles without Remember Me resume through the existing foreground authentication path. Additional scheduled windows use CPU/network and signed metadata bandwidth; the 30-second lease and platform backoff bound that cost. No phone installation, app-data reset, or live server change was performed.
