# Exact-device provisioning and reconciliation prerequisite — dev.102

This continues dev.100 rather than enabling production enrollment. Production Node and Android application owners still use the default-closed GroupLedger/GroupKeyManager; no approval RPC or user-facing action is activated yet. Physical enrollment is pending.

The existing GroupKeyManager has an explicit gated multi-device mode. Structural roster validation retains exact unique Peer IDs, eight-device-per-account limits and one canonical role per account. Key creation/acceptance additionally requires an exact match to all devices of the signed ledger. An authenticated roster entry with only account equality never authorizes a key. Current-generation handoffs use the existing protected Storage/DeliveryManager format; removal cancels pending handoffs and a new membership generation receives a fresh key. New devices receive no prior generation keys automatically.

The existing MessageLayer now resolves the authenticated sender and local Profile by both account and exact enrolled device, retaining the original envelope format and per-device signatures. A sibling cannot sign another sibling's envelope. Internal sender account/device attribution and protected history/dedupe remain unchanged.

The shared bounded approval parser verifies both existing device identities and the signed inner ledger event. The reconciliation helper accepts only exact consecutive authenticated server snapshots, current authorized approver, same-account target, inherited role, exact one-device add/revoke and matching signed ledger before/after. It verifies on a copied ledger and commits no partial mutation. It does not trust discovery, issue grants, distribute keys, persist records or own networking/retries. A default-closed ledger still rejects a cryptographically valid approval. Future application integration must supply the authoritative authenticated snapshots and persist the accepted signed event before key work.

Focused CNG and portable envelope tests passed for sibling key handoff, future encrypted messaging, exact sender attribution, signature substitution rejection, durable dedupe, absent historical keys, unapproved server entries, role inconsistency, revocation cancellation and key rotation. Native/server proof tests cover parser interoperability and negative nested evidence; reconciliation tests include exact admission, mapping/role/group/epoch substitution, disabled production gating, replay and explicit revoke/re-enroll. These are isolated host tests, not Android Keystore or physical transport acceptance.

Remaining activation work: publish authenticated target possession evidence, expose scoped proof submission/receipt projection, reconcile signed replicas on existing application workers, wire explicit normal UI confirmation, and test real multi-device key/session/message propagation. Android groups/attachments/history/media remain subsequent approved milestones, not implicitly complete.

The earlier immutable dev.101 build is retained as intermediate evidence, not this checkpoint's final candidate. Review found that the independent roster/ledger comparison also needed its own duplicate-device-slot check (the key manager's structural apply already rejected duplicates). The final dev.102 helper now rejects repeated Peer IDs, so duplicated roster rows cannot stand in for an omitted distinct enrolled device. This does not enable any production enrollment or weaken admission.
